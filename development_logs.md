## 3. Setting up from nothing

Already done on this machine. Recorded so it can be repeated.

```bash
npm install
```

Create the application's login role. It must **not** be a superuser or own
anything: row-level security does not apply to a table's owner, so running
as the owner would silently switch off every Area-isolation policy.

```bash
psql -h localhost -U postgres -c "CREATE ROLE appconn LOGIN PASSWORD 'appconn_dev_2026' NOSUPERUSER NOCREATEDB NOCREATEROLE;"
```

Create `.env` in the project folder (git-ignored):

```ini
PORT=3000
PGHOST=localhost
PGPORT=5432
APPCONN_PASSWORD=appconn_dev_2026
PG_SUPERUSER=postgres
PG_SUPERUSER_PASSWORD=123456
TOKEN_SECRET=<any long random string>
MEDIA_DRIVER=fs
MEDIA_ROOT=./media
```

Use forward slashes in paths.

Then build and seed the databases:

```bash
npm run db:reset
npm run seed
```

### The Android app

`native/android` is a Gradle project (Gradle 9.1 wrapper, Android Gradle
Plugin 9, Kotlin 2.3, Jetpack Compose; minSdk 26, targetSdk 36). The API
client is **generated from `spec/` on every build** (OpenAPI Generator
7.26, run as a plain Java task), so the app cannot drift from the server's
contract. From `native/android`, in Git Bash:

```bash
export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"
./gradlew assembleDebug testOneDebugUnitTest
```

**Three test phones on one handset.** Debug builds come in three copies —
`one` (the app, "NCL Colony Maintenance"), `two` ("Portal 2 (test)") and
`three` ("Portal 3 (test)") — each under its own package, so each has its
own Keystore key and data and registers as a separate phone for a separate
person (register each with a different mobile; the development OTP is shown
on screen). This is how one handset carries a complaint through every role:
the inspector may never be the person who did the work, so switching roles
in one copy cannot. Release builds are `one` only.

To run it on the phone against the portal on this PC (`npm start` running):
enable USB debugging, or pair once with **Wireless debugging → Pair device
with pairing code** (`adb pair <ip>:<port> <code>`; the phone must be on the
same network). Then:

```bash
adb reverse tcp:3000 tcp:3000
adb install -r app/build/outputs/apk/one/debug/app-one-debug.apk     # two/…two-debug.apk, three/…three-debug.apk
```

`adb reverse` makes `http://127.0.0.1:3000` on the phone this PC's portal,
so no firewall rule is needed. Only debug builds may speak plain HTTP, and
only to 127.0.0.1 and localhost; a release build is HTTPS only. The debug
app's "Portal address (development)" link changes the address.
`adb reverse` is lost when the phone disconnects; run it again.

### Architecture in one paragraph

Two databases. `ncl_identity` owns people, role assignments, devices,
premises and scope and
is a **shared service** — the E&M portal will be built on it. `ncl_maint`
owns tickets, SLA, contracts and media, and reads read-only copies
(`premises_ref`, `device_ref`) of identity data, because row-level
security cannot look across a database boundary. In this build the copies
are refreshed by function calls (`syncProjections`, `syncOne`);
production will use logical replication. A person proves who they are with an approved phone's key (the app) or,
for NCL employees on the web, Employee ID and password; that gives a
short-lived person token, and choosing a role gives an access token for
that one role assignment. Every query runs in a transaction whose
`app.role`, `app.scope_path`, `app.actor_id` (the role assignment),
`app.person_id`, `app.premises_id`, `app.contract_id`, `app.device_id` and
`app.auth_method` come from the token and nowhere else, set with `SET LOCAL` so a pooled
connection cannot carry one user's scope into the next request.
Background work asserts `app.role='SYSTEM'` deliberately; an unset role is
refused.

## 7. Rules for working on this

- **Run the tests before claiming anything works.** Every significant
  defect in this project was found by running something, not by reading
  it.
- **`npm run spec:check` is not optional.** Six specified endpoints once
  went unimplemented for five iterations, and nineteen implemented ones
  were never specified. The Kotlin and Swift clients are generated from
  the specification, so an endpoint missing from it does not exist for
  them.
- **A test that does not assert is worse than no test.** One suite called
  `/tickets/{id}/feedback` for four iterations without checking the
  status; it 404'd and the suite reported success. Three of the four
  matrices likewise could never fail until 2026-09-24. Check status codes
  and exit codes.
- **Clean database for suites, matrices and the simulation.** Ticket
  history is append-only and cannot be cleared, by design. There is no
  cleanup script and there should not be one.
- **Connect as `appconn`**, never the owner, or RLS is not being tested.
- **Every fix to a control gets a test that fails first.**
- **Comments explain why, not what.** Several controls look like
  over-engineering until you know the defect behind them. Keep prose
  plain — civil engineers read this, not only developers.
- **Commit with git.** The baseline as received is commit `fc45ee1`.

### Mistakes this project has already made

- **A rule written for the final state, applied to an intermediate one.**
  Twice: every occupant device had to have a premises (a *pending*
  registration has none), and every inspection photograph a geo-tag (the
  row exists before the image). Both made the feature impossible to start.
- **Visibility mistaken for authority.** A resident could approve their own
  registration, because they could see it and the device table had no
  write policy.
- **Guarding one column and no others.** The transition trigger guarded
  `state`; a contractor could still extend their own deadline and erase
  their own escalation count.
- **A permissive policy used to restrict.** PostgreSQL OR-s permissive
  policies, so "GM is read-only" silently granted full write. Use
  `AS RESTRICTIVE`.
- **A join that multiplied rows.** `sla_breach` is one-to-many and double
  counted tickets in the contract report. Aggregate before joining.
- **A background job that silently did nothing.** The escalation sweep
  had no `SYSTEM` branch in the row policy and processed zero tickets,
  with no error, for as long as it existed.
- **A request gate satisfied by a request.** Asking for an upload link
  created a media row, which opened the completion gate without any photo.
  All photo gates now require `upload_state='STORED'`.
- **An uncapped sweep.** After downtime the SLA sweep ran 129 seconds in
  one transaction. Now capped at 500 escalations a run, oldest first.

## 10. Break-glass — emergency access to the databases

Decision: README §5.5. Nobody works on the data as the database superuser.
When it cannot be helped — a complaint stuck by a fault, an investigation
across Areas, checking a restore — this is the only way in.

**Before:** get the approval in writing (an order or e-mail number) from
someone other than the person who will do the work. Decide read-only or
read-and-write; read-only unless a correction is the point.

**Open** (on the server, from the project folder):

```bash
npm run break-glass -- open --operator "S. Rao, Manager (Systems)" --approver "GM (Civil)" --reference "HQ/CIV/2026/117" --reason "JNT/2026/00042 stuck in Assigned after the 7 Oct outage" --mode read --minutes 60
```

It prints a login, a password and the `psql` line. The GM (Civil) and the
HQ System Administrator see "Emergency database access opened" in the
portal at once.

**While open:**

- The login reads both databases across every Area. In write mode it may
  insert and update, never delete, truncate or alter tables.
- The database's rules still apply. A change to a complaint needs the
  capacity stated first, inside a transaction:
  `BEGIN; SET LOCAL app.role = 'SYSTEM'; UPDATE …; COMMIT;` — and that,
  like every statement, is in the server's log. History and the audit
  log stay append-only whatever is stated.
- PostgreSQL refuses the login once the time is up, closed or not.

**Close** as soon as done, saying what was done:

```bash
npm run break-glass -- close --session <id> --note "reassigned the ticket; nothing else changed"
```

**Every day** (or from the scheduler): `npm run break-glass -- sweep` closes
anything past its time and records it as expired. `list` shows every
session; `verify` checks the register's hash chain and its file copy and
exits 1 if either was tampered with.

**Keep:** the server's PostgreSQL log (it holds the statements) and
`logs/break-glass.log`, copied off the server, for the two-year retention
period. A dropped trigger on the register or an edited row shows up in
`verify`; a missing file copy shows up as a count that differs.
